Last evening I decided to nose around the DZE file format, generated by the venerable [DayZ Editor](https://steamcommunity.com/sharedfiles/filedetails/?id=2250764298). The DZE format is the "native" save file format of the editor, and is the usual output as well. The recommended way of using edits from the editor is to load files in this format with a special mod.

It is, to the best of my knowledge, a bespoke format.  It may be documented somewhere online, and it could be reverse engineered from the mod (or better, the loader mod), but I wanted to take a stab at it going in blind. As I poked around the format I kept a running stream-of-conciousness document open.  This post is that document, tidied up to make it understandable from outside my head.

# The Setup

I needed some small, sample files, so I fired up editor and made three.  On one I placed a single tree. The second was the same tree, but I ticked all the checkboxes in the properties. The final one was deleting a single tree.

To help, I recorded some values from the editor itself.  For the `add_tree.dze` I got the object classname (`bldr_plnt_t_malusDomestica_3s_summer`), the position (`4134.939, 223.920, 10927.966`) and the orientation (`99.00`, `1.23`, `4.56`).  For `delete.dze` I didn't grab the position or orientation (I probably should have), only the classname, (`TreeHard_t_populusNigra_3sb_summer`)

Well, some things jump right out, don't they?  First off, lots of ASCII strings in there.  A couple are obvious, `EditorBinned` looks like a marker for the format, `Enoch` is the name of the DayZ mission (that's the name of Livonia), and I can see the classname of the tree I deleted, as well as a reference to the 3D model (`...summer.p3d`)

A less obvious string is `76561198043841050`.  I only recognize that because I see it somewhat regularly, it's my Steam ID.

Before each string there is a pattern, `XX 00 00 00`.  This looks like a length encoding; so a string entry would be an integer "how long is the string" and then the string bytes.  At four bytes, it's probably a little endian `uint32`, and if we check them, it does match up: `0x0c == 12 == len("EditorBinned")`.

# How about those floats...

Ok, so that clears a lot out, but leaves a lot to decode.  One thing we know should be in here are the position and orientation floats.  I wrote a little Go to encode those so we know what to look for (sadly, I can't do IEEE 754 in my head);

```go
package main

import (
	"encoding/binary"
	"os"
)

func main() {
	f, err := os.Create("floats.bin")
	if err != nil {
		panic(err)
	}
	defer f.Close()
	binary.Write(f, binary.LittleEndian, 4134.939)
	f.Write([]byte{0, 0, 0, 0})
	binary.Write(f, binary.LittleEndian, 223.920)
	f.Write([]byte{0, 0, 0, 0})
	binary.Write(f, binary.LittleEndian, 10927.966)
	f.Write([]byte{0, 0, 0, 0})
	binary.Write(f, binary.LittleEndian, 99.0)
	f.Write([]byte{0, 0, 0, 0})
	binary.Write(f, binary.LittleEndian, 1.23)
	f.Write([]byte{0, 0, 0, 0})
	binary.Write(f, binary.LittleEndian, 4.56)
	f.Write([]byte{0, 0, 0, 0})
}
```

# Wait, why did that change?

The diff also showed some other changes.  The position and orientation had changed, but that was expected because one of the tick boxes gave the tree physics and it fell over.  The other change was more suspicious;

```diff
32c32
< ┃00000091│ e6 a4 90 6a e6 a4 90 6a ┊ 01 00 00 00             │xxxjxxxj┊x⋄⋄⋄    │ Unknown   ┃
---
> ┃00000091│ fd a4 90 6a e6 a4 90 6a ┊ 01 00 00 00             │xxxjxxxj┊x⋄⋄⋄    │ Unknown   ┃
```

It's up in the metadata/header area of the file, right after the second Steam ID value.  Why would that change, but only a little bit?

Well, one obvious reason is perhaps a timestamp.  This file was saved after the first `add_tree.dze`, so maybe it's a timestamp that updated?  But 12 bytes is too big for a timestamp, what would that even unpack into?  The `01 00 00 00` looks like another length one, so let's drop that and see what the top 8 bytes decodes to.

```go
package main

import (
	"encoding/binary"
	"fmt"
)

func main() {
	var t uint64
	binary.Decode([]byte{
		0xfd, 0xa4, 0x90, 0x6a,
		0xe6, 0xa4, 0x90, 0x6a,
	},
		binary.LittleEndian,
		&t,
	)

	fmt.Println(t)
}
```

```
$ go run main.go
7678818674203993341
```

Ok, that is _way_ too big. Even assuming nanosecond precision, if that's a unix timestamp it's for the year 2213.  Looking at the diff again, I noticed on the fist file it's the same 4 bytes twice.  That'd be a wild coincidence for a timstamp, so what if it's actually _two_ timestamps? Created and modified?


```go
ackage main

import (
	"encoding/binary"
	"fmt"
)

func main() {
	var ta, tb uint32
	binary.Decode([]byte{
		0xe6, 0xa4, 0x90, 0x6a,
	},
		binary.LittleEndian,
		&ta,
	)

	binary.Decode([]byte{
		0xfd, 0xa4, 0x90, 0x6a,
	},
		binary.LittleEndian,
		&tb,
	)

	fmt.Println(ta, tb)
}
```

```
$ go run main.go
1787864294 1787864317
```

Well look at that, two timestamps, and they are even from today.  That seems like a match!

# Wrapping Up

At this point most of the file is accounted for, with some odds and ends remaining.

The `08 00 00 00` at the top is almost certainly a file version, I'll have to gather some old DZE files to know for sure.

We have a couple `01 00 00 00` left in as well, we will assume those are field counts similar to the `03 00 00 00` for the floats.  We don't know what they do exactly, but they seem to be carrying information themselves.  I _think_ the one after the timestamps is probably a count of the object entries that follow.

The biggest unknown segment is the `00 00 80 3f 1e 00 00 00 00 00 00 00`.

One thing I forgot to inject in my test files was a scale factor I could search for. The default scale it `1.00`, so it _should_ be in here somewhere.  Encoded that is `00 00 80 3f`, which we _do_ have in that unknown section. Another one bytes the dust!
